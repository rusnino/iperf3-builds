# Расширение платформенного покрытия iperf3-builds

## Цель

Расширить набор готовых статических сборок iperf3 для максимально широкого спектра Linux-платформ:

- серверов и рабочих станций;
- одноплатных компьютеров;
- сетевого и embedded-оборудования;
- промышленных систем;
- FPGA-based Linux-систем;
- устаревших, редких и экспериментальных архитектур.

Не привязывать матрицу сборок к конкретному дистрибутиву, производителю или классу устройств.

OpenWrt, Debian и другие системы могут использоваться как источники информации о существующих платформах и как тестовые окружения, но не должны определять границы проекта.

Основная единица покрытия — совместимый профиль бинарника: ОС + ISA + ABI + endianness + CPU/FPU requirements.

## 1. Сохранить уже реализованное

В проекте уже предусмотрены 15 Linux static targets:

`x86_64`, `x86`, `aarch64`, `arm`, `armhf`, `armv7`,
`mips`, `mipsel`, `mips64`, `mips64el`,
`powerpc`, `ppc64le`, `s390x`, `riscv64`, `loongarch64`.

Для каждого предусмотрены plain и auth-варианты.

Также сохранить:

- Linux x86_64 dynamic/dynamic-auth;
- macOS universal2/universal2-auth;
- существующие имена архивов;
- автоматическую публикацию releases;
- SHA256SUMS;
- upstream release watcher;
- повтор неудачных jobs;
- keepalive workflow.

Не переписывать сборочную систему целиком и не добавлять заново уже существующие функции.

README заявляет QEMU smoke tests. Проверить их реализацию в scripts и расширять существующий механизм, а не создавать параллельный.

## 2. Провести аудит текущих targets

Основная точка интеграции Linux static targets:

`scripts/build-static.sh`

Для каждого существующего target определить:

- target triple;
- источник и версию toolchain;
- libc и её версию;
- ISA и минимальное поколение CPU;
- разрядность и endianness;
- ABI;
- floating-point ABI;
- обязательные инструкции и CPU extensions;
- параметры сборки iperf3;
- параметры сборки OpenSSL для auth;
- проверки ELF;
- runtime-тесты и используемое окружение.

Особенно уточнить реальные значения:

- `x86` — минимальное поколение CPU;
- `arm` — заявленный ARMv5 soft-float;
- `armhf` — заявленный ARMv6 hard-float;
- `armv7` — заявленный ARMv7 hard-float;
- MIPS targets — ISA baseline, o32/n32/n64, soft/hard-float;
- PowerPC targets — CPU baseline и ABI.

Не менять существующие публичные имена только ради унификации. Их точное значение раскрыть в документации и метаданных.

## 3. Вести каталог совместимых профилей

Создать или расширить единый машиночитаемый каталог targets.

В нём хранить:

- публичное имя target;
- параметры совместимости;
- параметры toolchain;
- поддержку plain/auth;
- уровень стабильности;
- способ тестирования.

Не поддерживать вручную несколько расходящихся списков архитектур в scripts, workflow и документации.

По возможности использовать каталог как источник данных для CI matrix и таблицы поддерживаемых платформ.

Различать:

- новое семейство ISA;
- новый ABI существующего семейства;
- новый endian-вариант;
- профиль с более консервативными CPU/FPU requirements;
- оптимизированную сборку без расширения совместимости.

В первую очередь добавлять профили, которые позволяют запустить iperf3 на ранее не покрываемых системах.

## 4. Кандидаты на расширение

Список ниже — очередь технического исследования, а не обещание поддержки всех комбинаций.

### Первая очередь: недостающие варианты существующих семейств

Исследовать:

- `armeb` — ARM big-endian;
- `ppc64` — PowerPC64 big-endian;
- `riscv32` — RISC-V 32-bit;
- MIPS n32 BE/LE;
- дополнительные ARM/MIPS soft-float профили, если текущие сборки их не покрывают.

Для каждой новой комбинации установить, расширяет ли она фактическое покрытие.

Например, не добавлять отдельную ARM soft-float сборку только из-за другого поколения CPU, если существующий консервативный профиль уже совместим с нужными системами.

### Вторая очередь: дополнительные embedded ISA

Исследовать:

- ARC: ARC700 и ARC HS;
- SuperH: SH4 и необходимые endian/FPU-варианты;
- MicroBlaze: BE/LE;
- OpenRISC: `or1k`;
- Motorola 68k: `m68k`;
- C-SKY;
- Xtensa для Linux.

Не считать Linux-порт семейства гарантией совместимости со всеми процессорами этого семейства.

Для Xtensa и других конфигурируемых ISA явно указывать профиль целевого CPU.

Поддержку микроконтроллерных SDK и RTOS не смешивать с Linux-сборками: это отдельное направление портирования.

### Третья очередь: редкие и специализированные платформы

Исследовать при наличии рабочего toolchain и тестового окружения:

- `aarch64_be`;
- `sparc` / `sparc64`;
- `alpha`;
- `hppa` / `parisc`;
- `x32`;
- `hexagon`;
- `powerpcspe`.

Исторические архитектуры рассматривать отдельно как best effort. Не включать их в обязательную матрицу только ради количества targets.

### Другие операционные системы

Расширение ОС считать отдельным направлением от расширения Linux ISA/ABI.

Текущие macOS-сборки сохранить. Возможные Windows, BSD, Android и другие варианты оценивать отдельными задачами с собственными требованиями к toolchain, runtime, упаковке и тестированию.

Не считать Linux-бинарник автоматически поддерживаемым на другой ОС только из-за совпадения CPU.

## 5. Feasibility-проверка каждого нового target

Для каждого кандидата:

1. Найти пригодный toolchain.
2. Определить доступную libc и возможность статической линковки.
3. Собрать актуальную целевую версию iperf3.
4. Проверить ELF и отсутствие динамических зависимостей.
5. Выполнить доступные runtime-тесты.
6. Отдельно проверить OpenSSL и auth-вариант.
7. Оценить воспроизводимость сборки и стоимость сопровождения.
8. Зафиксировать ограничения.

Musl использовать преимущественно там, где её порт подходит для задачи. Не исключать архитектуру автоматически только потому, что для неё потребуется другая libc.

Если plain работает, а auth недоступен:

- разрешить plain-only target;
- явно указать ограничение;
- не публиковать фиктивный auth-артефакт.

Если требуется устаревшая версия iperf3, вынести такую поддержку в legacy-категорию и не смешивать с актуальными сборками.

## 6. Интеграция с CI

Существующие стабильные targets продолжать собирать текущим release pipeline.

Новые непроверенные targets сначала собирать отдельным вручную запускаемым experimental workflow, по возможности используя тот же build script.

Причина: текущая release job зависит от всей stable build matrix. Непроверенная архитектура не должна блокировать публикацию работающих сборок.

После подтверждения работоспособности переносить target в stable matrix.

Для новых платформ учитывать поддержку auth явно:

- plain + auth;
- plain-only.

Не запускать заведомо неподдерживаемые комбинации.

Не скрывать ошибки стабильных сборок общим `continue-on-error`.

## 7. Проверки бинарников

Проверить существующую реализацию и обеспечить для каждого Linux static артефакта:

- правильный ELF machine;
- разрядность;
- endianness;
- ABI attributes, где доступны;
- отсутствие `PT_INTERP`;
- отсутствие `DT_NEEDED`.

Проверять также auth-вариант, включая отсутствие случайных динамических зависимостей OpenSSL.

Не ограничиваться успешной компиляцией или выводом `ldd`.

## 8. Runtime-тестирование

Расширять уже существующие smoke tests.

Целевой набор:

- `iperf3 --version`;
- запуск сервера;
- короткий TCP-тест;
- короткий UDP-тест;
- reverse mode;
- несколько параллельных streams;
- JSON output;
- проверка authentication для auth-варианта, где возможно.

Использовать timeout и гарантированную очистку фоновых процессов.

Различать уровни проверки:

- `hardware-tested`;
- `system-emulation-tested`;
- `user-emulation-tested`;
- `build-only`.

Указывать конкретные тестовое окружение, CPU model и выполненные проверки.

Не выдавать user-mode эмуляцию за проверку совместимости с ядром целевого устройства и не использовать эмуляцию для оценки реальной производительности.

## 9. Метаданные и документация

Если manifest ещё отсутствует, включать его внутрь существующих архивов.

Хранить:

- версию iperf3;
- target name и triple;
- ISA/ABI/endianness;
- CPU/FPU requirements;
- compiler/libc/OpenSSL versions;
- build flags;
- результаты ELF checks;
- уровень runtime-проверки;
- ограничения совместимости.

Minimum kernel указывать только с понятным основанием. Различать заявленный минимум toolchain/libc и реально проверенную версию.

В README добавить общую таблицу:

| Target | ISA / CPU baseline | ABI | Endianness | FPU requirements | Auth | Testing | Limitations |
|---|---|---|---|---|---|---|---|

Примеры устройств и дистрибутивов допустимы как дополнительная информация, но не как границы поддержки.

Отдельная обязательная таблица OpenWrt не требуется.

## 10. Публикация новых архитектур для существующих версий

Существующий watcher обнаруживает отсутствующие release tags, а не недостающие архитектуры внутри уже опубликованных releases.

Поэтому после добавления stable target вручную запустить сборку выбранной версии.

Учесть, что текущая публикация использует `--clobber` и может перезаписать существующие assets.

Если позднее будет реализована выборочная сборка targets, обеспечить корректный SHA256SUMS для всех актуальных архивов релиза, а не только для текущего запуска.

Selective rebuild не является обязательным условием первого этапа.

## 11. Критерии включения в stable

Новый target считается поддерживаемым, если:

1. Однозначно определены его ISA, ABI и CPU/FPU requirements.
2. Зафиксирован пригодный toolchain.
3. Сборка воспроизводимо проходит в CI.
4. Проверена заявленная статическая линковка.
5. Указаны выполненные runtime-тесты и их ограничения.
6. Установлен статус auth.
7. Работают упаковка и публикация.
8. Обновлены каталог targets и README.
9. Понятно, какую ранее не покрываемую группу систем он добавляет.

Не прошедшие эти условия targets остаются experimental или build-only.

## Ожидаемый результат

Максимально широкий и прозрачно описанный набор работающих сборок iperf3.

Приоритет — не количество названий архитектур, а возможность выбрать подходящий бинарник для разнообразных систем и понять:

- требования к CPU и ABI;
- необходимость дополнительных runtime-компонентов;
- наличие authentication;
- уровень проверки;
- известные ограничения.
